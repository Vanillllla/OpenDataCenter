# Network Bandwidth Engine — 0.6.1.4-alpha

## Граница этапа

Новый движок рассчитывает виртуальную пропускную способность, но не заменяет `ClusterScheduler`, `FixedResources`, `TaskConsole` и начисления экономики до 0.6.1.7. Никаких новых ресурсов CPU/GPU, приоритетов задач или формул контрактов. Номиналы устройств, существующие 4/8 портов коммутатора и их 100/1000 Мбит/с не изменены. `SwitchLimits` — общий источник старых характеристик. Физические Data Cable и оптоволокно не имеют самостоятельного лимита.

## API и единицы

- `BandwidthEngine.Node`: UUID, тип, установленная ёмкость в Мбит/с, доступность.
- `BandwidthEngine.Edge`: UUID, endpoints, FIBER/UPLINK/PATCH, номинал и ограничение порта, доступность. Ёмкость PATCH ограничена и кабелем, и портом; NIC и коммутатор имеют отдельные общие лимиты.
- `BandwidthEngine.Request(id, server, peer, requested, reserved)`: `peer == null` означает WAN; иначе передача между двумя серверами. Полоса задаётся в десятичных Мбит/с, не во внутренних десятых долях `TaskEngine`. Резерв не превышает запрос. Запросы с одинаковым ID запрещены.
- `Result.devices` и `Result.links`: номинал, доступная локальная ёмкость (0 при недоступности), обслуженная полоса, свободный локальный остаток, отдельно LAN и WAN. Свободная ёмкость устройства **не равна** гарантированной свободной ёмкости маршрута.
- `Result.requests`: исходный запрос и резерв, обслуженная часть резерва, обслуженная полоса, недостача, маршруты с фактическим расчётным потоком, список ограничивающих UUID. `Result.wan/lan` — суммарная обслуженная полоса запросов, без повторного сложения последовательных узлов. Все результаты являются расчётными, не измерениями реального трафика.

## Алгоритм

Для WAN допустимы пути антенна → терминал → коммутатор → сервер. LAN внутри коммутатора идёт через него и два PATCH, между коммутаторами — через общий терминал и два UPLINK. Локальные пути не содержат антенну. Каждый общий ресурс списывается один раз на проходящую единицу потока. Для LAN оба направления используют общий лимит, отдельный full-duplex бюджет не вводится.

Равное прогрессивное заполнение одновременно повышает обслуженную полосу каждого активного запроса. Внутри запроса доли сначала равны между терминалами, затем между антеннами одного терминала; при исчерпании ресурса закрывается соответствующий путь, остаток идёт по другим. Резервы обрабатываются первой фазой, дополнительные незарезервированные заявки — второй. Это не приоритеты задач. Стабильная сортировка по UUID/ID исключает зависимость от порядка обхода коллекций.

Для фазы, содержащей только WAN, при недостаче дополнительно вычисляются max-min справедливые целевые значения (бинарный поиск общей прибавки и Dinic max-flow на графе с расщеплёнными вершинами). Если равномерный алгоритм может их достичь, сохраняется его раскладка; иначе поток разлагается на допустимые пути. Это позволяет перенести гибкий запрос с ограниченного маршрута, необходимого другому запросу. При fallback баланс между терминалами не является отдельным математическим оптимумом. Для смешанного LAN/WAN используется общий прогрессивный алгоритм; оптимизация многотоварного потока с глобальным перераспределением уже занятых путей не реализована. В частности, смешанные запросы могут не использовать весь теоретически достижимый максимум.

## Интеграция с миром

`BandwidthTopology` строится по всему измерению, а не по одному GUI или LAN. Общая антенна имеет один лимит даже для нескольких дата-центров. Доступность оптических маршрутов проверяется по непрерывным верифицированным кабелям; логические uplink активны при подтверждённом физическом LAN-соединении. Проверяются существующие порты и дубликаты устройств. Выгруженная/неподтверждённая инфраструктура не выдаёт фиктивной ёмкости. Пока это консервативный расчёт для верифицированной сети; виртуальные выгруженные сети будут подключены на этапе 7.

`PhysicalNetwork.bandwidth(World)` — единый серверный результат измерения, обновляемый при обращении и после цикла симуляции (раз в 20 тиков). Активные незавершённые задачи формируют WAN-запросы по сохранённым NETWORK bindings (`amount` уже в Мбит/с), ключ — UUID задачи + UUID сервера. Пауза исключает вычислительные сетевые резервы. Запрос не переносится на другое оборудование. Никакой новой логики запуска или оплаты здесь нет; старое распределение продолжает работать независимо. Локальные запросы поддерживаются чистым API, но пока не создаются действующими контрактами.

`BandwidthCache` кэширует маршрутизируемый граф по структурным метаданным, revision uplink и revision верифицированных позиций. Смена старого счётчика использования или названия не инвалидирует граф. Результат пересчитывается при изменении фиксированных запросов. Временный GUI читает рассчитанную загрузку устройства; `logicalView` отдаёт рассчитанную загрузку линий. Stage 5 использует тот же результат для сетевой карты.

## Проверки

Автономная проверка `BandwidthEngineTest` входит в `tools/test-core.sh`, `tools/test-core.ps1`, Gradle `verifyBandwidthEngine`. Проверены: один/несколько терминалов, общий источник в отдельных LAN, несколько антенн, равное распределение и fallback с конкуренцией, резервы, все три LAN tiers, NIC/порт, LAN без WAN, разрыв/восстановление, изменение запросов, детерминизм при перемешивании входа, случайные графы и 320 серверов/40 коммутаторов/12 терминалов с перегрузкой. Остальные автономные тесты и проверка ресурсов также запускались. Полная компиляция Forge 1.12.2, NBT и игровая интеграция не проверены (нет JDK 8 и подготовленных зависимостей).
